# Changelog and Commit Standards

## 1. Формат сообщений коммитов (Conventional Commits)

- Используйте Conventional Commits (`feat`, `fix`, `perf`, `refactor`, `docs`, `chore`) с областью видимости: `<type>(<scope>): <краткое описание>`.
  - Примеры областей: `feat(multihop): ...`, `fix(xray): ...`, `feat(reality): ...`, `fix(store): ...`, `fix(node): ...`, `feat(billing): ...`.
- **Обязательно включайте подробное тело коммита** с пунктами:
  - **Что изменилось:** конкретные файлы, модули и технические правки.
  - **Зачем:** решаемая проблема или архитектурная мотивация.
  - **Влияние на производительность и безопасность:** аллокации, блокировки, влияние на фаервол.
- `release-please` читает темы коммитов, а не заголовки Pull Request. Нестандартный заголовок коммита будет проигнорирован при генерации Release PR.

---

## 2. Коммиты синхронизации с Upstream

- При слиянии или подтягивании изменений из `AppsGanin/rospanel` используйте фиксированный формат темы:
  ```
  feat: sync upstream <версия/тег> preserving fork safeguards
  ```
  или
  ```
  chore: sync upstream <версия/тег> preserving fork safeguards
  ```
- В теле коммита явно перечисляйте:
  - Диапазон подтянутых коммитов upstream.
  - Проверенные компоненты форка (мульти-хоп, REALITY-доноры, миграции, лимиты устройств).
  - Результаты прогона тестового набора.

---

## 3. Ведение Changelog и Release PR

- `release-please` формирует черновик Release PR автоматически.
- При подготовке или слиянии Release PR **всегда обогащайте release notes и `CHANGELOG.md`** подробными описаниями и буллетами из тела коммитов (на русском и английском языках, если релиз публичный).
- Перед мержем релизного PR строго соблюдайте процедуру навыка [rospanel-release-lab](.agents/skills/rospanel-release-lab/SKILL.md).
