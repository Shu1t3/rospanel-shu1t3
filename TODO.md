# Переезд мастер-ноды

## Цель

Развернуть новый мастер на другом сервере, проверить его работу и переключить на него существующий публичный домен. URL подписок (`https://<тот же домен>/<путь>/<токен>`), пользовательские токены и ссылки, уже импортированные в приложения, должны сохраниться. Для планового переезда действия администратора после первоначальной настройки DNS должны быть сопоставимы с добавлением обычной ноды: создать переезд в UI, выполнить одну команду на новом сервере, проверить статус и нажать «Переключить».

**Границы гарантии:** DNS не обеспечивает мгновенное обновление адреса у всех клиентов. Старый сервер должен обслуживать обращения на старый IP в течение периода ожидания. Если он погиб до переключения, восстановление возможно из последней внешней копии; потеря изменений равна её возрасту. Автоматическое переключение DNS требует доступа к API используемого DNS-провайдера. Без него UI предлагает ручное изменение записи и честно показывает, что сценарий уже не соответствует целевой простоте.

## Файлы и подсистемы

- `cmd/rospanel/service.go`, `cmd/rospanel/cli.go`, `install.sh`: режим кандидата/старого сервера, одноразовая команда установки, запуск и остановка служб.
- `internal/backup/`, `internal/store/`: согласованный снимок SQLite и каталога данных, перенос `secrets.key`, проверка версии схемы, финальная синхронизация.
- Новый `internal/migration/`, `internal/server/` и `internal/core/`: протокол спаривания, проверки, блокировка второго активного мастера, управление фазами, API и журнал событий.
- `internal/nodeagent/`, `internal/nodeapi/`, `internal/core/manager_nodes_views.go`: переподключение нод и режим ожидания на старом сервере, который продолжает обслуживать клиентов с закешированным IP.
- `web/src/Management.tsx`, `web/src/api.ts`, `web/src/i18n/{ru,en}.ts`: мастер переезда, прогресс, ошибки, подтверждение переключения и откат до окончательного отключения.
- `internal/sub/sub.go`, `internal/server/subscription.go`: сохранить контракт URL подписки; проверить выдаваемые адреса и все форматы конфигураций после переноса.

## Шаги

### 1. Зафиксировать инварианты и предусловия

- [x] Разделить в модели **публичный домен** (не меняется) и **технический адрес кандидата** (нужен только для установки и проверки). Не подменять `Settings.Host` техническим адресом.
- [x] Проверять владение доменом, доступность нового сервера извне, DNS A/AAAA, порты и сертификат. Подготовить сертификат для публичного домена на кандидате до переключения: перенос действующего сертификата из защищённого снимка либо выпуск через DNS-01; продление после переключения проверить отдельно.
- [x] Определить DNS-адаптер для реально используемого провайдера и хранение его учётных данных. Поддержать установку малого TTL до миграции, изменение всех релевантных A/AAAA, проверку ответа авторитативных DNS и явное сообщение о кешировании у клиентов. Ручной режим оставить как fallback.
- [x] Задать состояния переезда: `подготовка → копирование → кандидат готов → переключение → ожидание → завершено`, а также `ошибка/откат`. Разрешить только один переезд и одного активного мастера; повторный запрос операции должен быть безопасным.

### 2. Развернуть и проверить кандидат одной командой

- [x] В UI выдавать одноразовую команду установки, похожую на добавление ноды. Токен спаривания должен быть короткоживущим, показываться один раз и передаваться по проверенному TLS; его нельзя писать в логи.
- [x] Запускать новый сервер в пассивном режиме: он принимает снимок и проверки, но не ведёт фоновые задания, не принимает платежи и изменения, не рассылает уведомления и не публикует VPN-конфигурацию до повышения в мастер.
- [x] Делать согласованный снимок БД (включая незавершённый WAL) и нужных файлов, а не копировать живую БД как обычный файл. Проверять целостность, совместимость схемы, расшифровку секретов, права файлов и достаточное место. Передача и временное хранение снимка должны быть защищены; временные копии удаляются после завершения.
- [x] Проверять на кандидате вход администратора, генерацию подписки с прежним URL и токеном, работу каждого включённого протокола, TLS, оплат, фоновых интеграций и связь с обычными нодами через технический адрес. Показать результаты по отдельности и запретить переключение при обязательной ошибке.

### 3. Выполнить управляемое переключение

- [x] Ввести fencing: старый мастер прекращает **все** изменения состояния перед финальным снимком, включая UI/API, ботов, платежные callback, фоновые задания, выдачу новых токенов, привязку устройств и приём отчётов нод. Запросы, не зафиксированные до снимка, не должны получать успешное подтверждение.
- [x] Передать финальный согласованный снимок; проверить контрольные показатели (пользователи, токены, ноды, настройки, платежи, счётчики/последние отчёты). Повысить кандидат в активный мастер и только затем изменить DNS. Исключить автоматический перезапуск старого мастера в активном режиме.
- [x] Обеспечить переподключение обычных нод к тому же публичному домену. На время DNS-кеша обращения, попавшие на старый IP, должны попадать на новый control plane; не оставлять два экземпляра, независимо обрабатывающих записи или подтверждающих отчёты.
- [x] Проверить публичный домен с внешней точки: подписка по прежнему URL во всех форматах, веб-панель, TLS, node-sync, платежный callback и новые VPN-подключения. Показать администратору факт переключения и статус каждой проверки.

### 4. Дождаться ухода клиентов со старого IP и отключить старый сервер

- [x] Добавить режим ожидания для прежнего мастера: сохранить VPN-обслуживание клиентов с закешированным IP, но отправлять управление, подписки и изменяемые запросы на новый мастер. Передавать новому мастеру трафик и состояние этого VPN-сервера без потери или двойного учёта; для этого отобразить бывший локальный сервер в модель обычной ноды с переносом ключей, настроек и прав доступа.
- [x] В UI показывать активные подключения и последние обращения к старому IP, прошедшее время после смены DNS и ошибки синхронизации. Кнопка «Отключить старый сервер» доступна после проверок; допускается явное принудительное завершение с предупреждением о клиентах, которые всё ещё используют старый IP.
- [x] После отключения прекратить синхронизацию и очистить временные права/токены переезда. Не удалять старый сервер или резервную копию автоматически до окончания согласованного окна отката.

### 5. Добавить аварийное восстановление и документировать порядок действий

- [x] Расширить существующие резервные копии до проверяемого внешнего хранения с расписанием, шифрованием, уведомлением об ошибке и периодическим пробным восстановлением. Показывать дату последней пригодной копии и ожидаемую потерю изменений (RPO).
- [x] Добавить восстановление нового мастера одной командой из такой копии, даже если старый недоступен. Сохранить публичный домен, путь и токены подписок; после проверки переключить DNS и показать, какие изменения могли быть потеряны.
- [x] Описать плановый переезд, аварию, откат **до** DNS-переключения и откат **после** него. После начала записи на новом мастере возврат на старый запрещён без обратной синхронизации, чтобы не создать расходящиеся БД.

## Проверка и критерии готовности

- [x] Интеграционный сценарий: действующая панель с пользователями, платежами и несколькими нодами → установка кандидата одной командой → проверки → переключение → отключение старого сервера. Ранее выданный URL подписки и токен совпадают побайтно, а клиент получает рабочие конфигурации после обновления.
- [x] Проверить Base64/обычные ссылки, Clash, sing-box, Xray JSON, страницу подписки и QR; права доступа и пользовательские ключи сохраняются. Ноды продолжают синхронизацию без повторного join.
- [x] Проверить прерывания на каждом этапе: ошибка копирования, повреждённый снимок, несовместимая схема, ошибка TLS/DNS, рестарт кандидата, отказ старого мастера до/после финального снимка. Ни один сценарий не должен приводить к двум активным мастерам или подтверждённым, но не перенесённым записям.
- [x] Проверить период DNS-кеша: подключения к обоим IP обслуживаются, subscription/API-запросы на старый IP читают актуальное состояние нового мастера, трафик учитывается один раз; после отключения старого сервера новые подключения через домен работают.
- [x] Аварийный прогон из внешней копии на чистом сервере с недоступным старым мастером. Зафиксировать фактическое время восстановления (RTO) и максимальную потерю изменений (RPO); не заявлять нулевые RTO/RPO без измерений и репликации.
